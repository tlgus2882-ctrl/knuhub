# 접근 규칙은 RLS에 두고, 데이터는 서버에서 다룬다 (업로드만 예외)

공개 범위, 마감일, 역할, 연락처 공개 범위 같은 접근 규칙은 모두 Postgres RLS와 DB 함수에 둔다. 화면이나 서버 코드에서 같은 규칙을 다시 구현하지 않는다. 그래야 규칙이 한곳에만 있고, 역할별 사용자로 Supabase를 직접 호출하는 테스트 하나로 검증할 수 있다.

읽기는 서버 컴포넌트에서, 쓰기는 Server Action에서 한다. 로그인한 사용자의 세션(쿠키)으로 Supabase를 호출하므로 RLS가 그대로 적용된다. 학번으로 메일을 찾는 조회나 가입 도메인 검증처럼 서버에서만 해야 하는 일이 있어서 이 방식을 택했다.

예외로, 제출 파일 업로드는 브라우저에서 Storage로 바로 보낸다. 서버를 거치면 Vercel의 요청 크기 제한(약 4.5MB)에 걸려 20MB 제출물을 받을 수 없기 때문이다. Storage 접근 권한도 같은 규칙(RLS)으로 막는다.

Secret key는 RLS를 우회하므로 테스트 준비, 관리자 작업, 그리고 DB가 사용자에게 일부러 막아 둔 서버 전용 조회(예: 학번으로 메일 찾기, #5)에만 쓴다. 이런 조회도 DB 함수로 만들어 service_role에만 실행 권한을 주고, 서버 코드는 그 함수만 부른다.

탈퇴(#19)도 secret key를 쓴다. 사용자를 지우는 일(auth admin API)과, 마감이 지나 본인도 지울 수 없게 된 제출 파일을 Storage에서 지우는 일은 사용자 권한으로 할 수 없기 때문이다. 탈퇴해도 되는지와 지울 파일 목록은 여전히 DB 함수(`prepare_withdrawal`)가 정하고, 서버는 그 결과대로만 지운다.

AI 검토처럼 바깥 API를 부르는 일(#47)은 RLS가 막을 수 없다. 이런 호출은 서버에서만 하고(API 키는 서버 환경변수에만 둔다), 부르기 전에 서버 액션이 기존 DB 함수(예: `is_professor_or_assistant`)로 권한을 확인한다. 권한 규칙 자체는 여전히 DB 함수에만 있다.

GitHub 공개 저장소로 제출(#56)은 업로드 예외의 두 번째 길이다. GitHub의 압축 파일 주소는 브라우저에서 받을 수 없으므로(CORS) 서버가 받아 업로드 준비를 거친 뒤, 그 학생의 세션으로 Storage에 올리고 같은 `submit_files()`로 제출한다. 학생 권한으로 올리므로 Storage 정책과 제출 함수가 그대로 막는다. 서버는 정해진 GitHub 주소(codeload.github.com, api.github.com)만 부르고, 학생이 넣은 주소는 소유자·저장소·브랜치로만 읽는다.
